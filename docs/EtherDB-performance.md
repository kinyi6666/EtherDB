- **定位先分清：不同赛道，不要当同款产品比。** TDengine 是平台级产品（分布式集群、生态、运维体系）；EtherDB 是**边缘 / 单机**定位，专打**事件驱动的突发高速写入**（雷达采样这类），不搞大规模集群。本文的同机对比是**标定差距**，不是同赛道对决。

### 4.3 流式查询：1002 万行怎么拉（2026-09-21 查询优化后重写）

这个测试**刻意对齐了 TDengine 官方示例的取数方式**：计时从 `query` 之前开始，到所有行被取完为止，中间包含网络往返、服务端执行和客户端取行指针——也就是说，这是**端到端**的取数耗时，不是服务端内部耗时。

```sql
SELECT ts,col_int FROM perftest20.perf_data_2 WHERE col_int>5
```

命中 10,019,994 行（不是抽样，是全量拉完）：

```
query() 首批耗时 :    58.15 ms (网络RTT + 服务端执行 + 首批发序列化)
流式拉取总耗时   :  1491.22 ms (后续 FETCH 批次 + 取行指针)
总耗时           :  1549.37 ms , total records 10019994
  [OK] 行数一致: 10019994
```

**约 1.55 秒拉完 1002 万行 → 约 647 万行/秒**（两列，单线程客户端）。*（同一条 SQL 在 `perf_data_1` 上复测：首批 55.41 ms、总耗时 1577.66 ms，可复现。）*

这次提升来自三件事（优化前的瓶颈拆解保留在 7.2 节作为历史存档）：

1. **列式零拷贝游标**：`fetchRow(const void** row)` 直接返回**指向接收缓冲中原始列数据的指针**，遍历只是推进游标，不再构造任何类型化对象；
2. **传输格式精简**：长度前缀只对字符串等变长类型使用，定长列不再每格携带 4 字节长度；
3. **值解析挪到调用方**：库只交付原始字节，要不要解析、怎么解析由调用方决定——**解析耗时不进入本测试计时**，与 `taos_fetch_row` 的语义完全对齐，公平比较。

值得单独说的是首批耗时从 142 ms 降到 55~58 ms：服务端分块产出、客户端收到第一批就能开始消费——**首字节延迟和总吞吐是两件独立的事**。

> ✅ **更新（2026-09-21）**：同一张 1002 万行表、同一条 SQL，EtherDB 现在约 **1.55 秒**，**反超 TDengine 3.4.2.8 的逐行接口约 1.3 倍**（2.06 秒），比 2.1.7.2 逐行（2.12 秒）快约 1.35 倍。唯一的保留项：2.1.7.2 的块接口 1.21 秒仍比我们快约 28%，详见 7.2——优化前的旧数字（11.26 秒）在附录 C 里留档。

## 五、为什么能跑到这个数：几个工程决定

### 5.1 写入路径：内存表 + 提交队列 + WAL

```
INSERT → MemTable(skip-list) → commit queue → 后台提交线程
                                    ↓
                            WAL 记录 + 按天分区列式文件
```

- 写入先落**跳表 MemTable**，不在写路径上做任何磁盘随机 IO；
- 提交由**独立后台线程**完成，mem / imem 双缓冲，落盘期间写入不阻塞；
- **WAL** 保证崩溃可重放，并可按 WAL 大小异步触发提交，也支持同步提交模式。

### 5.2 存储格式：列式 + 时间分区 + 两阶段压缩

- 数据**按时间有序、列式**存放于按天分区的文件中，范围扫描和列投影天然高效；
- 压缩分两阶段：**第一阶段**用类型特化算法（布尔位打包、整数 delta + zigzag + Simple8B 风格位打包、浮点、字符串），**第二阶段**可选 **LZ4**；可配置为「关闭 / 单阶段 / 两阶段」；
- 本次测试中，单独建库写入的 **1002 万行数据文件只有 5.9 MB**（外加 SMA 0.8 MB、索引 30 KB。按定长 52 字节/行估算，逻辑原始数据约 521 MB）。

### 5.3 查询加速：块级 SMA 剪枝

每个数据块都带预计算的 **min/max/sum** 聚合（`.sma` 文件）。这让 `SUM / MIN / MAX / COUNT` 有快速路径，也能让 `WHERE` 过滤器**整块丢弃**不匹配的数据块——`COUNT(*)` 只要 0.34 ms（纯读块索引），带列过滤的 `COUNT(*) WHERE col_int < 5` 也只有 4.10 ms（SMA 让大部分块根本不用被解码）。

### 5.4 客户端 SDK：流式 + 背压

C 接口 + 面向对象的 C++ 接口，纯头文件加预编译库，**不需要服务器任何源码**。支持：预编译语句、参数绑定、行式与列式批量写入、**带背压的异步批量**、**流式取数**（**零拷贝游标**：逐行 / 逐块返回原始列指针，值转换由调用方按需完成）。

### 5.5 架构分层

`dnode / dbnode / vgroup` 三层模型（受 TDengine 启发），自研 RPC 与网络层：Linux 上 epoll，Windows 上 IOCP，线程模型由配置驱动。

**6124 万行、233 MB 常驻内存、1 MB 的服务端。** 没有 JVM 预热，没有一堆 `.so`，拷贝一个二进制就能跑——这依然是它最吸引我的地方。

> 关于内存多说一句：RSS 会随测试阶段在 170 ~ 240 MB 之间波动（内存表、查询缓冲、多线程 arena），不是随行数线性增长的「数据常驻」——数据是列式压缩存在文件里的。

内置 HTTP 监控端点，直接吐 Prometheus 格式，不用额外装 agent：

```
$ curl http://127.0.0.1:9187/api/v1/health
{"status":"ok"}

$ curl http://127.0.0.1:9187/metrics
# HELP db_connections_total Total number of accepted client connections
db_connections_total 43
# HELP db_slow_queries_total Total number of queries slower than the threshold
db_slow_queries_total 0
...
```

另有 `/api/v1/status`、`/api/v1/metrics/list`、`/api/v1/slowlog`。

## 七、和 TDengine 比怎么样？——这次连最新的 3.4 也测了

上一版文章的遗憾是「TDengine 在 Windows 上没部署成功，所以没比」（后来在 D2000 上补了 2.1.7.2 的对比）；2.1.7.2 的对比里又留了一句「3.x 换了代，本表不代表它现在的水平」。**这次把最后一块拼图补上：本机部署了官方 Docker 镜像 `tdengine/tsdb:latest`（3.4.2.8.community，默认配置），用同版本官方客户端库重跑全套用例。** 两代 TDengine 的结果并排贴出。

**先把定位区分开：这不是同一条赛道的对决。** TDengine 是**平台级产品**——分布式集群、多副本、完整生态与运维体系，面向的是大规模生产系统；EtherDB 是**边缘 / 单机**定位的引擎，目标场景是「事件驱动的突发高速写入」——比如**雷达采样**、振动/声学采集这类**平时安静、事件一来就要瞬间吃下大量数据**的场合，它不搞大规模集群。本文把两者放在同一台机器、同一份数据上跑，是为了**标定差距、看清各自的设计取舍**，而不是宣布「谁替代谁」。要比集群、生态、SLA、工具链——TDengine 一直是、也会继续是更稳的选择。

- **同一台机器**：飞腾 D2000，客户端/服务端全在 loopback（3.4 为容器 `--net=host` 直连）；
- **同一份数据**：两边用同一套数据生成公式（微秒递增时间戳 + 严格递增 `col_int`），10 列定长 52 字节/行，1002 万行；
- **同一条 SQL**：`SELECT ts,col_int FROM perf_data WHERE col_int>5`，全量拉完，两边行数一致（10,019,994）；
- **同一测法**：写入都是预编译语句**列绑定**，10000 行/批；查询都是**官方客户端**端到端计时（t0 在 query 之前，t1 在最后一行取完之后）；
- **同一客户端版本**：3.4 测试使用**从容器提取的官方 3.4.2.8 客户端库**（`libtaos.so` + `libtaosnative.so`）编译链接——TDengine 3.4 要求客户端与服务端前三段版本号严格一致，否则服务端直接拒绝连接（`Version not compatible`）；
- TDengine 均为**默认配置**（3.4 库参数：`vgroups=2 / replica=1 / comp=2 / precision 'us'`，WAL 保留期 3600s）。

### 7.1 写入：对 3.4 快约 1.56 倍（对 2.1.7.2 是 2.6 倍）

| 测试 | EtherDB | **TDengine 3.4.2.8** | TDengine 2.1.7.2 |
|---|---|---|---|
| 列绑定写入（1 万行/批） | 平均 **2,146,648 行/秒**（2+100 轮） | 平均 **1,383,440 行/秒**（2+50 轮） | 平均 **830,951 行/秒**（2+50 轮） |
| 长跑（2+1000 轮，1002 万行，新表） | 平均 **2,105,169 行/秒** | 平均 **1,348,964 行/秒** | 平均 **816,893 行/秒** |
| 单批延迟 | 4.7 ~ 4.8 ms | 典型 7.2 ms | 12.0 ~ 12.8 ms |
| 波动（标准差/均值） | 6% ~ 9% | 4% ~ 15% | 3% ~ 18% |

**读法**：3.4 的写路径比 2.1.7.2 快了约 65%（83 万 → 138 万行/秒），这是实打实的进步；但在这台 D2000 上，EtherDB 仍快约 1.56 倍（长跑平均 210.5 万 vs 134.9 万）。长跑 1000 轮的平均值两边都只比短跑略低，**都没有明显衰减**；差距主要来自写入路径设计——EtherDB 的写路径只进内存表和 WAL，落盘全交给后台线程，客户端 `execute` 的等待时间（约 4.8 ms）明显短于 3.4 的 7.2 ms。3.4 的长跑出现过个别约 0.9 秒的停顿轮（把最小值拉到 11,367 行/秒），但对 1000 轮平均值的影响不到 2%（2.1.7.2 的长尾见附录 G）。

### 7.2 取数：优化后反超——约 1.55 秒，快过两代 TDengine 的逐行接口

（2026-09-21 更新：此前的 To-Do「零拷贝块游标」已落地，本节重写；旧版瓶颈分析保留在本节末尾的「历史存档」。）

| 取数方式（1002 万行 × 2 列） | EtherDB | **TDengine 3.4.2.8** | TDengine 2.1.7.2 |
|---|---|---|---|
| 逐行 / 游标接口（`fetchRow` / `taos_fetch_row`） | **约 1.55 s**（首批 55~58 ms） | 约 2.06 s（6 次测量中位） | 2.12 s |
| 批量接口（`etdb_fetch_block` / `taos_fetch_block`） | 未复测（优化前 11.55 s） | 约 1.66 s（2451 块） | **1.21 s**（3022 块） |
| 折算吞吐（逐行口径） | **约 647 万行/秒** | 约 486 万行/秒 | 474 万行/秒 |

**对 3.4.2.8 快约 1.3 倍；对 2.1.7.2 逐行快约 1.35 倍。** 从「输 5.5 倍」到反超，靠的是三件事：列式零拷贝游标（返回原始列指针，遍历不构造对象）、传输格式精简（长度前缀只给变长类型）、值解析移到调用方（与 `taos_fetch_row` 同语义，解析均不入计时）。

**两个诚实的补充：**

1. **对 2.1.7.2 的块接口（1.21 s）仍慢约 28%**：老版本的分块协议在这条路径上确实高效，这一项我们继续认账。
2. **3.4 的块接口反而退步**：3.4 块取数约 1.66 s，比 2.1.7.2（1.21 s）慢约 37%，逐行则基本持平（2.06 vs 2.12 s）。逐行/块各复测 6 轮，结论稳定（逐行 2.02~2.42 s，块 1.58~1.83 s）。原因不做猜测，数字照实贴出——换环境复现出不同结果，欢迎来对数据。

**历史存档（优化前的瓶颈拆解）**：旧 `fetchRow` 把每个值物化成 `std::vector<Value>`，逐值构造/拷贝在 1000 万行规模上非常可观；加上服务端每批「解码 + 序列化」（约 130 KB/批、77 个往返）——服务端日志显示每 5.8 万行解码+序列化约 35 ms，**服务端从来不是主要瓶颈**，大头在客户端 API 语义。

### 7.3 分页 / 聚合：EtherDB 快 3.6 ~ 185 倍（3.4 进步巨大，但 OFFSET 仍会增长）

同样 1002 万行表、同一批用例（各跑 3 次取平均，C API 客户端内计时）：

| 用例 | EtherDB | **TDengine 3.4.2.8** | TDengine 2.1.7.2 |
|---|---|---|---|
| `LIMIT 10 OFFSET 0` | 0.87 ms | 3.11 ms | 2.90 ms |
| `LIMIT 10 OFFSET 10000` | 0.82 ms | 3.22 ms | 4.71 ms |
| `LIMIT 10 OFFSET 100000` | 0.76 ms | 6.64 ms | 28.02 ms |
| `LIMIT 10 OFFSET 300000` | 0.82 ms | 14.6 ~ 18.7 ms | 80.70 ms |
| `LIMIT 10 OFFSET 500000` | **0.82 ms** | **22.35 ms** | **133.41 ms** |
| `COUNT(*)` | **0.34 ms** | **39.14 ms** | **122.19 ms** |
| `COUNT(*) WHERE col_int < 5` | 4.10 ms | 759.11 ms | 195.67 ms |
| `WHERE col_int < 5 LIMIT 10` | 8.91 ms | 1428.89 ms | 436.09 ms |

- **EtherDB 的 OFFSET 是「索引跳转」**：时间戳本身有序 + 块级 min/max 索引，OFFSET 加多少都不需要扫过前面的行，所以耗时是平的（0.8 ms）。
- **3.4 的 OFFSET 从「线性膨胀」改善为「缓增」**：`OFFSET 500000` 从 2.1.7.2 的 133 ms 降到 22 ms（快了 6 倍），但**仍随 OFFSET 增长**（0 → 50 万：3.1 → 22.4 ms），没有做到平坦。
- **`COUNT(*)` 3.4 快了 3 倍**（122 → 39 ms）：EtherDB 直接读块索引（0 数据 I/O），0.34 ms 完事，仍领先约 115 倍。
- **反直觉的一项：3.4 的带过滤全表扫描比 2.1.7.2 慢 3 ~ 4 倍**（`COUNT(*) WHERE col_int<5`：196 → 759 ms；`WHERE col_int<5 LIMIT 10`：436 → 1429 ms）。客户端 C API 与 CLI 两种方式复测一致、可重复。3.4 的 `COUNT(*)`（无过滤）走统计信息只要 39 ms，一旦带上 `WHERE` 列过滤（哪怕命中 5 行）就变成 759 ms——如实记录，不挑着报。

**照例说公道话**：（1）这些是「极快路径」的对决，绝对耗时都不大（除过滤扫描外都是毫秒级），业务里更常见的可能是带条件的长时段聚合，两边都要扫数据，差距会小得多；（2）过滤扫描这类「几乎全表扫描」的用例对所有引擎都不友好——EtherDB 的 4.10 ms 靠的是 SMA 整块剪枝，3.4 的 759 ms 是全扫的成本；换成真正能用上索引/时间范围的查询，3.4 通常会快很多。

### 7.4 资源与体积：EtherDB 仍然占优（3.4 的占用比 2.1.7.2 更大）

| 项目 | EtherDB | **TDengine 3.4.2.8** | TDengine 2.1.7.2 |
|---|---|---|---|
| 同规模数据落盘（1002 万行） | **22 MB**（数据 5.9 MB + SMA 0.8 MB + WAL 15.6 MB） | 数据 **12.1 MB**（data 10.7 + stt 0.9 + sma 0.5）+ WAL **497 MB**（默认保留期 3600s） | **39 MB**（数据文件 7.3 MB + WAL 33 MB） |
| 服务端进程 RSS | **233 MB**（持有 6124 万行） | **422 MB**（taosd；全套组件共 643 MB） | **314 MB**（taosd） |
| 服务端二进制 | **1.07 MB** | **123.7 MB**（taosd） | 2.79 MB |
| 客户端库 | 静态库 **224 KB** | **104.7 MB**（`libtaos.so` 22.5 MB + `libtaosnative.so` 82.2 MB，未 strip） | 动态库 **10.03 MB** |
| 服务端线程数 | 21 | 138 | 73 |

- **数据文件同一量级**：1002 万行的列式数据，EtherDB 6.7 MB、3.4 约 11.6 MB（含 stt）、2.1.7.2 7.3 MB。
- **WAL 差异是数量级**：EtherDB 约 15.6 MB；3.4 默认保留 1 小时，本次实测 497 MB（约等于原始数据量）；2.1.7.2 为 33 MB。在意磁盘的场景要按 3.4 的默认策略评估。
- **部署体积是设计路线差异**：1 MB 单文件 vs 805 MB 的 Docker 镜像（taosd 二进制 123.7 MB + 基础系统与全套组件）；客户端也从 224 KB 静态库变成 105 MB 的双动态库。

### 7.5 并发扩展：8 个进程齐写，把 8 核跑满

单个客户端进程喂不满 8 核——测试程序默认每轮之间留 100ms 间隔，单进程时服务端只用到 0.66 核；把间隔设为 0（连续模式）也只有 1.3 核。所以本节**同时启动 P 个进程，每个进程写自己的表（`perf_data_1..P`），连续压测**，看聚合吞吐随进程数怎么扩展。每进程 302 轮 × 1 万行 = 302 万行；8 进程合计 **2416 万行**。表为累加写入（未清表），TDengine 侧因此在中后段出现后台合并干扰（下文标注）。

| 进程数 P | EtherDB 聚合（各进程之和） | EtherDB 端到端 | EtherDB 整机 CPU（均/峰） | TDengine 3.4.2.8 聚合（和） | TDengine 端到端 | TDengine 整机 CPU（均/峰） |
|---|---|---|---|---|---|---|
| 1 | 200 万行/秒 | 104 万行/秒（2.9s） | 42.5% / 48.5% | 134 万行/秒 | 67 万行/秒（4.5s） | 46.0% / 49.6% |
| 2 | 322 万行/秒 | 178 万行/秒（3.4s） | 60.4% / 69.4% | 236 万行/秒 | 66 万行/秒（9.1s） | 46.6% / 61.1% |
| 4 | **609 万行/秒** | 228 万行/秒（5.3s） | 54.2% / 62.3% | 351~389 万行/秒 | 67~114 万行/秒（10.6~18.1s） | 48.7~68.1% / 68.3~85.8% |
| 8 | **618 万行/秒** | **254 万行/秒（9.5s）** | **79.1% / 86.5%** | 457~479 万行/秒 | 70~84 万行/秒（28.6~34.6s） | 48~52% / 71~82% |

（口径说明：「聚合」= 各进程自报平均速率之和（与全文其他写入数字同口径）；「端到端」= 总行数 ÷ 从启动到全部退出的墙钟，包含连接、提交等待等固定开销，更保守。整机 CPU 含约 21% 的后台基线（GitLab 容器、编辑器等），已单独测过空闲基线。）

- **EtherDB：4 进程摸到平台，8 进程主要收益是把 CPU 打满。** 聚合 200 万 → 322 万 → **609 万** → 618 万行/秒；2416 万行 9.5 秒写完（端到端 254 万行/秒）。8 进程时整机 CPU 平均 79%、峰值 86.5%，**扣除后台基线后基本跑满**——「至少 8 个进程才能跑满 CPU」的判断在本次实测成立。8 进程时各进程速率出现分化（58 万~129 万行/秒），排队压力已转到客户端侧，继续加进程收益很小。
- **TDengine 3.4.2.8：聚合随进程数增长，但高并发下出现停顿。** 134 万 → 236 万 → 351~389 万 → 457~479 万行/秒；但 8 进程时单轮最低跌到 **6,839 行/秒**（秒级停顿轮，最高 142 万），端到端墙钟不升反降（70~84 万行/秒；同样的 2416 万行要 29~35 秒，EtherDB 是 9.5 秒）。**这属于「本机、默认配置、表数据累加堆叠」条件下可重复的实测观察（两次复测均出现），成因不做断言。**
- **同口径对比（8 进程）**：聚合 618 万 vs 458~479 万（约 1.3 倍）；端到端 254 万 vs 70~84 万（约 3~3.6 倍）；整机 CPU 79%/86.5% vs 48~52%/71~82%。

### 7.6 结论（打平？并没有——各有胜负，看你用在哪儿）

| 维度 | 赢家 | 对 3.4.2.8（最新） | 对 2.1.7.2（对照） |
|---|---|---|---|
| 写入吞吐 | **EtherDB** | ~1.56× | ~2.6× |
| 并发写入（8 进程聚合） | **EtherDB** | ~1.3×（端到端 ~3×） | —（未测） |
| 全量取数（fetch all，逐行口径） | **EtherDB**（2026-09-21 优化后） | ~1.3× | ~1.35×（注：2.1.7.2 块接口仍赢 ~28%） |
| 分页 / COUNT / 过滤 | **EtherDB** | 3.6 ~ 185×（OFFSET 不衰减） | 3.3 ~ 359× |
| 磁盘（仅数据文件） | **EtherDB** | ~1.7× | ~1.1× |
| 磁盘（含默认 WAL） | **EtherDB** | ~23× | ~1.8× |
| 部署体积 | **EtherDB** | ~116×（1.07 MB vs taosd 123.7 MB；对镜像 ≈750×） | ~12× |
| 成熟度、生态、分布式 | **TDengine** | 不是一个量级的对手 | 同左 |

**适用面一句话**：如果你是「写入量大、查询模式以范围/分页/聚合为主、部署资源受限」的场景，EtherDB 的设计是有优势的，特别适合突发的高速采集，需要数据库快速写入；**全量取数这条老短板也已补上：1.55 秒拉完 1002 万行，反超 TDengine 3.4 的 2.06 秒**；如果你需要**成熟生态、分布式与运维体系**，TDengine（尤其新版本）依然是更稳的选择。

**定位再强调一次**：EtherDB 要打的不是「大集群平台」，而是**边缘节点上的事件突发写入**——雷达采样之类的场景：事件一来数据汹涌而至，必须瞬间高速吃下，平时负载很低；在意的是突发写入密度、单机资源占用和交付简单（1 MB 单文件 + 224 KB 客户端库），不在意集群、多副本、生态工具链。**按场景选型，不要按跑分表选型；要比平台能力（集群、生态、运维），这两个产品不在一个货架上。**

**最后照例声明**：TDengine 3.4.2.8 为官方 Docker 镜像默认配置，2.1.7.2 为本机老版本；测试数据是合成顺序数据（对两边的压缩和聚合都友好），单机 loopback 环境。**这些数字只对「这台机器、这两个版本、这份数据」负责。**

## 八、怎么上手

```bash
# 1. 启动服务端
./src/bin/etherdb_dserver -p 7040 -d ./etdb_data

# 2. 连上交互式 shell
./src/bin/etherdb -h 127.0.0.1 -p 7040 -u root -P etherdbdata
```

```sql
CREATE DATABASE testdb;
USE testdb;
CREATE TABLE sensor (ts TIMESTAMP, temperature FLOAT, humidity FLOAT);
INSERT INTO sensor VALUES(1716364800000, 25.5, 60.2);
SELECT * FROM sensor WHERE temperature > 25.0;
SELECT COUNT(*), AVG(temperature), MAX(temperature) FROM sensor;
```

**SQL 是 MySQL / TDengine 风格的**，`WHERE / GROUP BY / HAVING / ORDER BY / LIMIT / OFFSET / DISTINCT` 加聚合函数，没有需要现学的新查询语言。

Windows 用户：客户端 shell 与 SDK 都是现成的（服务端也支持 Windows 构建）；本次全量实测在 Linux（ARM）上完成。

## 九、适合谁，不适合谁

**适合**：

- 想要**能读懂全部源码**的时序数据库，而不是一个黑盒
- 边缘 / 嵌入式 / 单机场景：资源受限，装不了 JVM 和一堆依赖，拷贝一个二进制就要能用
- 千万级到亿级行的单机时序数据，需要 SQL 但不想要运维复杂度.
- **事件驱动的突发高速写入**（如雷达采样、振动/声学采集）：平时负载低、事件一来就要瞬间高吞吐落库，这种「突发密度」正是 EtherDB 写路径（内存表 + 提交队列 + WAL）针对的形态。
- 想学存储引擎、压缩算法、LSM / 列存实现的人（代码分层清晰，`src/etdb` 和 `src/query` 值得一读）

**不适合**：
- 需要成熟生态、大厂背书和 SLA 的生产核心系统
- 多节点分布式强一致集群（目前是单机为主，`dnode / dbnode / vgroup` 分层已经铺好，但集群能力有待开发）

- **语言**：C++17，从零实现，无第三方数据库引擎依赖（仅内置 LZ4）
- **平台**：服务端 Linux / Windows；客户端 shell 与 SDK 支持 Linux / Windows（本次全量实测为 Linux ARM）
- **联系**：kinyi6666@gmail.com
